# UGSci 专家 Agent 与协作工作流平台评审基线

> 日期：2026-08-02  
> 状态：问题基线，暂不代表最终技术方案  
> 范围：UGSci「专家」「专家团/协作工作流」的产品定位、前端体验、后端模型、OMP 编排、生产与科研适用性  
> 用途：后续按问题编号逐项设计、实现和验收

## 1. 文档目的

UGSci 的目标不是一个通用聊天机器人集合，也不只是一个“多个 Agent 互相
对话”的演示平台。它应当成为面向以下领域的专业 Agent 平台：

- 油气勘探：地震资料处理解释、构造解释、储层预测、含油气性评价、井位论证；
- 油气开发：测井解释、储层评价、储量计算、油藏工程、开发方案、动态分析、
  数值模拟、配产配注、提高采收率；
- 钻完井与生产工程：井身结构、钻井设计、完井方案、采油采气工艺、地面集输、
  完整性和运行优化；
- 地下储气库：选址评价、地质与油藏建模、注采能力、库容评价、运行优化、
  井筒与盖层完整性、风险预警、周期调峰；
- 科学研究：文献调研、问题定义、数据分析、模型构建、实验或模拟、结果复核、
  可重复性和论文/报告产出。

平台必须同时解决两类性质不同的问题：

1. **生产问题**：强调数据可信、流程合规、工具可控、结果可追溯、失败可恢复，
   以及最终建议的责任边界；
2. **科研问题**：强调探索空间、假设比较、证据链、可复现计算、不确定性表达，
   以及对反例和替代解释的保留。

本文件记录当前“专家与专家团”模块距离上述定位仍存在的差距，并给出后续
逐项改造所需的共同语义、目标架构和验收方向。

## 2. 总体判断

当前模块已经具备以下可用基础：

- 专家 Agent 的创建、配置、技能和 MCP 绑定；
- 预设专家团队和自定义团队；
- OMP 五阶段状态机：规划、分派、验证、综合、完成；
- 顺序、并行、主管、路由、评审循环、多方论证六类编排意图；
- fork 隔离、结构化交接文件、状态持久化和重试保护；
- 团队运行状态展示和聊天会话跳转。

但当前整体仍更接近：

> Agent 配置列表 + 由提示词约束的多 Agent 任务

距离目标形态仍有明显差距：

> 专业知识、数据、软件工具和质量规则驱动的领域 Agent 资产库  
> + 可持久化、可验证、可恢复的确定性协作工作流平台

最关键的矛盾不是“模式还不够多”，而是下列基础概念尚未完全分离：

- 专家模板与专家运行实例；
- 专业角色与 Agent 显示名称；
- 团队定义与工作流定义；
- 工作流拓扑与自然语言编排提示；
- 生产任务的强约束执行与科研任务的开放探索；
- 业务结果与执行过程、证据、软件产物之间的关系。

### 2.1 已确认的总体产品框架

本项目确认采用“一个侧边栏入口、三个内部业务入口”的总体框架。

侧边栏只保留一个入口：

> **专家·协作**

进入模块后，设置三个并列的一级入口：

1. **专家**：管理专业能力资产和可运行的专家实例；
2. **专家团**：面向开放式多专家讨论、联合研判和 OMP 动态协作；
3. **协作工作流**：面向显式流程、确定性控制、节点级状态和强可观测性。

三个入口共享专家模板、专家实例、角色、技能、工具和产物等底层模型，但产品
目标和执行语义必须保持清晰边界：

| 入口 | 核心问题 | 编排特点 | 典型产物 |
|---|---|---|---|
| 专家 | 谁具备什么专业能力，当前是否可用 | 单专家执行 | 专业分析、计算结果、单专家报告 |
| 专家团 | 多位专家如何围绕复杂问题形成判断 | OMP 动态规划、开放讨论、按需派生 | 共识、分歧、证据摘要、联合建议 |
| 协作工作流 | 任务必须经过哪些节点和控制点 | 显式拓扑、确定性调度、状态可观测 | 标准成果、完整过程记录、审批与证据链 |

该框架避免两个极端：专家团不会被强制变成僵硬的流程图；生产和科研标准流程
也不会完全依赖控制 Agent 的自由发挥。

## 3. 建议统一的产品概念

### 3.1 专家模板（Expert Template）

可复用的专业能力定义，不直接等同于一个正在运行的 Agent。建议包含：

- 稳定 `expert_template_id`；
- `role_key`，例如 `reservoir-engineer`、`well-integrity-reviewer`；
- 专业范围与明确边界；
- 输入数据契约；
- 输出成果契约；
- 推荐技能、MCP、计算软件和模型；
- 工具权限与数据权限；
- 默认质量检查和验收规则；
- 适用阶段：勘探、评价、开发、生产、储气库运行、科研等；
- 版本、来源、维护人和验证状态。

### 3.2 专家实例（Expert Instance）

专家模板在具体 Agent 工作区中的运行实体。建议包含：

- 稳定 `agent_id`；
- 引用的 `expert_template_id` 和模板版本；
- 实际模型、工作区、知识库、记忆和软件连接；
- 当前健康状态；
- 是否允许作为工作流控制器；
- 最近运行、成功率、平均耗时和人工评价；
- 本地定制覆盖项。

### 3.3 能力角色节点（Capability Role Node）

工作流中的执行节点。它可以：

- 绑定一个长期专家实例；
- 由 OMP 按专家模板临时派生；
- 由路由器在运行时选择具体实例；
- 在生产环境中限定为经验证的指定实例。

工作流节点不应只保存专家名称，而应保存稳定角色和绑定策略。

建议支持四种绑定策略：

- `fixed_instance`：必须使用指定且已验证的专家实例；
- `preferred_instance`：优先使用指定实例，不可用时按策略降级；
- `template_spawn`：按专家模板由 OMP 临时派生；
- `dynamic_route`：根据能力、健康状态、权限和成本在运行时选择实例。

### 3.4 专家团（Expert Team）

专家团是面向开放式复杂问题的多专家协作定义。它强调讨论目标、参与角色和协作
策略，不要求用户预先定义完整 DAG。

典型能力包括：

- OMP 根据问题自主规划和分解；
- 固定专家、优先专家和临时派生专家混合参与；
- 独立分析、并行汇聚、多轮反馈、反驳和共识形成；
- 根据中间结论动态增加角色或追加调查；
- 保留分歧、少数意见、假设、不确定性和待补充数据；
- 输出结构化联合结论，并允许作为协作工作流中的一个节点被调用。

现有顺序交接、并行汇聚、主管协作、智能路由、评审迭代和多方论证，应继续作为
专家团的 OMP 协作策略进行完善。在专家团模块中，它们描述讨论组织方式，不承诺
生产流程级的确定性拓扑。

### 3.5 协作工作流（Collaboration Workflow）

一套可版本化、可执行的任务定义，至少包括：

- 工作流 ID 和版本；
- 使用场景和风险等级；
- 输入参数及数据类型；
- 节点、依赖边、并行组、条件、循环和汇聚规则；
- 各节点的角色、指令、工具和权限；
- 超时、重试、失败降级和人工审批点；
- 证据、结果和中间产物契约；
- 成功标准与终止条件。

协作工作流可以直接调用专家节点，也可以包含“专家团讨论节点”：把某个开放式
研判任务交给专家团，再将其结构化结论交给后续确定性节点。

### 3.6 工作流运行（Workflow Run）

工作流定义的一次不可混淆的执行实例，建议具有独立 `run_id`，记录：

- 使用的工作流版本、专家模板版本和 Agent 实例；
- 输入数据快照或引用；
- 每个节点的状态、日志、工具调用和产物；
- 路由和决策理由；
- 失败、重试、恢复和人工介入记录；
- 最终报告、证据清单和质量结论。

## 4. 领域任务设计原则

### 4.1 生产任务与科研任务不能共用同一默认治理强度

建议给工作流增加任务类型和治理等级：

| 类型 | 典型场景 | 默认策略 |
|---|---|---|
| `production_advisory` | 动态分析、配产建议、注采优化 | 强数据校验、强工具白名单、必须审查 |
| `production_execution` | 可能影响实际生产系统的操作 | 人工审批、最小权限、完整审计、默认禁止自动外部写入 |
| `engineering_design` | 开发方案、钻完井方案、储气库运行方案 | 多专业会签、约束检查、版本冻结 |
| `research_exploration` | 假设探索、方法对比、文献调研 | 允许分支探索，要求来源和可复现记录 |
| `research_validation` | 模型复算、结果复核、论文审查 | 独立复算、盲审或对照试验、保留负结果 |

### 4.2 领域结论必须连接到证据和产物

“建议提高注气量”不能只是语言模型生成的一句话。至少应能追溯到：

- 使用了哪些井、层段、时间范围和数据版本；
- 是否完成单位、坐标、缺失值和异常值检查；
- 使用了什么公式、脚本、模拟器及其版本；
- 哪些假设成立，哪些数据缺失；
- 不确定性、适用范围和风险是什么；
- 哪位专家或哪个验证节点给出通过结论。

### 4.3 计算软件应是一等工作流资源

ECLIPSE、CMG、tNavigator、OPM、Petrel、Techlog、PIPESIM、OLGA、
COMSOL、Python 科学计算等不应只作为普通工具名称存在。工作流需要记录：

- 软件能力和版本；
- 许可证与可用性；
- 输入文件契约；
- 运行参数和资源需求；
- 输出解析器；
- 运行超时与失败分类；
- 可重复运行所需的环境信息。

### 4.4 人工专家是工作流中的合法节点

高风险生产决策、资料解释歧义和方案审批必须允许设置人工会签节点，而不是
默认由另一个 LLM Agent 代替责任人。

## 5. 当前问题清单

问题按优先级编号。`P0` 表示会影响正确性或数据一致性；`P1` 表示平台能力
和可维护性缺口；`P2` 表示体验和效率问题。

### P0-01：专家团运行按钮与 OMP 自动派发逻辑冲突

**现象**

- 团队卡声明缺少实例时可以由 OMP 自动派发；
- 启动逻辑也支持找不到指定主控时回退到任意可用 Agent；
- 但团队卡仍在主控名称匹配失败时禁用“运行工作流”。

**影响**

- 部分预设团队无法启动；
- 页面表达与真实执行能力相互矛盾；
- 用户无法理解“已有专家”和“临时角色”的区别。

**方向**

- 仅在没有任何可用控制器时禁用；
- 显示“控制器”“绑定实例”“OMP 临时派生”三种状态；
- 运行前进行可执行性检查并列出降级项。

### P0-02：使用名称和包含关系匹配专家实例

**现象**

团队成员主要保存显示名称，并通过精确或包含关系查找 Agent。

**风险**

- 改名后失效；
- 同名或相似名称误匹配；
- “油藏工程师”和“油藏工程师 Copy”存在歧义；
- 无法安全迁移、导入导出或跨设备同步。

**方向**

- 保存稳定 `agent_id`、`expert_template_id` 和 `role_key`；
- 名称仅用于显示；
- 导入旧数据时提供一次性解析和人工确认。

### P0-03：后端通过专家名称推断角色，忽略显式角色信息

**现象**

分派提示构建中多处调用 `resolve_role(name)`，没有优先使用成员定义中的
稳定角色键。

**风险**

- 自定义名称可能退化为通用角色；
- 角色工具隔离、技能白名单和专业提示词可能不生效；
- 生产任务中可能获得超出预期的工具权限。

**方向**

- 成员模型增加强类型 `role_key`；
- 后端只允许注册已知角色或显式自定义角色定义；
- 角色解析失败必须报错或进入受限默认角色，不能静默放宽权限。

### P0-04：自定义工作流存在前端和后端两份真源

**现象**

- 前端列表保存在浏览器 `localStorage`；
- 后端只在运行前注册定义；
- 前端删除不会删除后端记录；
- 后端列表接口只返回 ID 和名称，无法还原完整定义。

**风险**

- 换浏览器或清理缓存后定义丢失；
- 同一工作流前后端内容不一致；
- 删除、编辑和运行历史无法可靠关联；
- 无法进行版本管理和团队共享。

**方向**

- 后端成为唯一真源；
- 提供完整 CRUD、版本号和乐观锁；
- `localStorage` 仅保留草稿或缓存；
- 明确个人工作流、项目工作流和系统预设工作流的所有权。

### P0-05：每次运行可能重复注册新的自定义团队记录

**现象**

后端未收到稳定 ID 时使用名称加秒级时间戳生成团队 ID；前端运行注册请求
没有提交前端已有的稳定 `team.id`。

**风险**

- 同一团队多次运行产生多份后端记录；
- 记录上限触发后可能按时间清理；
- 运行历史无法稳定聚合到一个工作流定义。

**方向**

- 创建时持久化一次并返回稳定 ID；
- 编辑使用 `PUT/PATCH`；
- 运行只引用工作流 ID 和版本，不再隐式创建定义。

### P0-06：专家创建不是原子操作

**现象**

模板创建依次执行创建 Agent、写入 `AGENTS.md`、读取并更新配置。中间失败
会留下半创建实例。

**风险**

- 出现无提示词、无正确权限或配置不完整的专家；
- 用户重试后产生重复实例；
- 后续工作流可能错误选中不完整实例。

**方向**

- 后端提供原子化 `create-from-template` 服务；
- 或实现补偿删除和幂等键；
- 创建后执行健康检查，成功后再标记为可用。

### P0-07：工作流拓扑主要由提示词约束，不是引擎级约束

**现象**

六类编排模式具有不同提示词，但顺序、并行、路由、评审循环和多方论证主要
依赖控制 Agent 按文字执行。自定义步骤被拼入首轮提示，再由模型写入计划。

**风险**

- 模型可能跳步、改变顺序或遗漏输出；
- 前端显示拓扑和实际执行路径可能不同；
- 条件、循环次数和失败策略难以可靠验证；
- 同一工作流难以重复得到一致执行过程。

**方向**

- 定义正式 `WorkflowDefinition`；
- 调度器确定性执行 DAG，LLM 只负责节点内部推理；
- 运行时记录实际路径并与定义进行一致性校验。

### P0-08：前端编排参数没有被 Gate 强制执行

**现象**

评审轮数、路由说明和验收标准目前主要进入提示文本；Gate 仍使用全局固定
重试限制。

**风险**

- 用户设置的“最多两轮”不一定等于真实限制；
- 生产工作流无法依赖配置进行治理；
- 页面显示与执行事实可能不一致。

**方向**

- 将执行策略写入不可随意修改的运行状态；
- Gate 强制执行轮数、超时、预算、并发和终止条件；
- 提示词只解释策略，不承担策略 enforcement。

### P1-01：前端通过斜杠命令启动正式工作流

**现象**

前端拼接 `/ugsci-team <mode> <team-ref> <task>` 并发送聊天消息。

**问题**

- 缺少正式类型契约；
- 输入转义、长任务和复杂参数难处理；
- 不利于幂等、权限检查和结构化错误返回；
- 工作流运行与聊天协议耦合。

**方向**

提供 `POST /workflows/{id}/runs`，返回 `run_id` 和绑定的 `chat_id`。
斜杠命令继续保留为人工快捷入口，但内部调用同一个领域服务。

### P1-02：缺少工作流完整 CRUD 和版本管理

当前后端只有注册、简化列表和状态读取，缺少详情、更新、删除、复制、发布、
版本冻结和导入导出。

建议状态至少包括：`draft`、`validated`、`published`、`deprecated`。
生产工作流运行时必须固定使用一个已发布版本。

### P1-03：状态 API 只返回某控制 Agent 工作区中的最新实例

**问题**

- 不能查看全部运行；
- 无法按团队、项目、井、区块或储气库查询历史；
- 切换当前 Agent 会改变看到的状态；
- 缺少取消、暂停、恢复、重试、节点重跑和人工介入接口。

**方向**

建立独立运行索引和接口：

```text
GET  /workflow-runs
GET  /workflow-runs/{run_id}
POST /workflow-runs/{run_id}/cancel
POST /workflow-runs/{run_id}/resume
POST /workflow-runs/{run_id}/retry
POST /workflow-runs/{run_id}/nodes/{node_id}/retry
```

### P1-04：缺少领域数据契约

目前任务输入主要是自然语言模板。生产和科研都需要结构化输入定义，例如：

- 项目、区块、井、层、储气库和时间范围；
- LAS、DLIS、SEGY、RESQML、ECLIPSE/CMG deck、生产动态表等文件；
- 单位制、坐标系、深度基准和版本；
- 数据质量状态与保密等级。

建议引入 `InputSchema`、`ArtifactSchema` 和领域数据验证节点。

### P1-05：缺少证据链和结果契约

当前结果主要表现为聊天输出和若干 JSON 文件。应统一定义：

- `finding`：结论；
- `evidence`：数据、文献、计算或模拟证据；
- `assumption`：关键假设；
- `uncertainty`：不确定性及范围；
- `recommendation`：建议；
- `risk`：风险与限制；
- `artifact`：图件、表格、模型、脚本、deck、报告；
- `review`：验证结论和签署信息。

### P1-06：缺少人机协同和审批节点

生产执行、方案发布、重要参数变更和高风险建议应支持：

- 人工确认输入数据范围；
- 专业人员会签；
- HSE、完整性或合规审批；
- 外部系统写入前的最终授权；
- 驳回后携带意见返回指定节点。

### P1-07：专家缺少健康状态和适用性评价

“启用”不代表专家可执行任务。至少需要检查：

- 模型是否可用；
- 必需技能和 MCP 是否存在；
- 计算软件是否安装、许可是否有效；
- 数据权限是否满足；
- 系统提示词和角色配置是否完整；
- 最近一次自检和真实任务是否成功。

### P1-08：专家模板缺少版本、来源和验证状态

科研方法、行业规范和公司流程会变化。专家模板需要记录来源、版本、适用标准、
测试集和验证结论，避免“提示词被修改后所有历史结果含义改变”。

### P1-09：专家模板与专家实例混为同一层

当前页面同时承担创建角色模板、配置 Agent 实例、查看技能和直接对话。应拆分：

- 模板资产库：定义专业能力；
- 实例管理：模型、工作区和连接；
- 运行入口：开始单专家任务；
- 评测中心：验证专家质量。

### P1-10：生产工作流和科研工作流缺少差异化模板

当前六种模式是通用协同拓扑，并没有表达生产和科研的不同方法论。

建议优先设计领域模板：

**生产类**

- 资料质检 → 解释/计算 → 独立复核 → 方案建议 → 人工会签；
- 动态监测 → 异常识别 → 原因诊断 → 措施候选 → 风险审查；
- 储气库日/周运行分析 → 库容与压力检查 → 注采能力预测 → 调峰建议；
- 井筒/盖层完整性异常 → 多源证据汇聚 → 风险分级 → 应急建议。

**科研类**

- 文献检索 → 证据分级 → 研究空白 → 假设形成；
- 数据探索 → 多方法建模 → 交叉验证 → 统计与物理一致性审查；
- 模拟实验 → 参数敏感性 → 不确定性分析 → 可复现产物归档；
- 作者 Agent → 独立复算 Agent → 反方审稿 Agent → 编辑综合。

### P2-01：专家列表存在 N+1 请求和静默降级

页面先获取 Agent 列表，再为每个 Agent 分别获取配置、技能和 MCP。11 个专家
可能产生 34 次请求。子请求失败会被转换为空数据，用户无法区分“确实为空”
和“加载失败”。

**方向**

- 增加专家摘要聚合接口；
- 卡片只加载摘要，详情按需加载；
- 对部分失败显示明确的降级状态和重试入口。

### P2-02：专家卡片信息密度过高但决策信息不足

当前卡片同时展示长描述、模型、大量技能标签、MCP、状态和操作。页面中多个
专家显示“126 个技能”，不能帮助用户判断专业适配性。

**方向**

卡片只保留：

- 专业定位；
- 健康状态；
- 3～5 个核心能力；
- 模型或运行配置；
- 最近使用/质量指标；
- “开始任务”和“配置”。

完整技能、MCP、知识库和提示词进入详情页或抽屉。

### P2-03：“召唤专家”动作含义不够明确

用户难以判断它是打开聊天、创建实例、临时运行还是激活 Agent。建议根据真实
行为使用“开始对话”“运行单专家任务”或“创建实例”等明确文案。

### P2-04：专家团空闲状态占用过多首屏空间

没有活跃运行时，状态区域仍占据较大高度，导致工作流列表下移。

**方向**

- 空闲时折叠成单行状态；
- 活跃时展开运行面板；
- 已完成时进入“最近运行”，不要长期占据主入口。

### P2-05：页面级主操作没有随标签切换

进入专家团标签后，页面右上角仍显示“创建专家”，同时内容区又有“创建专家团”。
建议顶级主按钮随当前上下文切换为“创建专家”或“创建工作流”。

### P2-06：术语不统一

当前混用“专家团”“团队”“协作工作流”“工作流模式”“主控”“协调者”。建议：

- 产品一级名称：协作工作流；
- 预设/自定义对象：工作流模板；
- 参与者集合：专家角色；
- 运行中的组织：执行团队；
- 主导节点：控制器或主管节点，避免同一语义多种称呼。

### P2-07：工作流创建弹窗未来扩展能力有限

当前单页滚动弹窗适合简单模板，但不适合条件、循环、人工节点、数据契约和
失败策略。建议最终改为四步向导：

1. 目标、场景、风险等级和输入；
2. 选择工作流模板；
3. 配置角色、节点、工具和治理策略；
4. 预览拓扑、检查可执行性并发布。

### P2-08：缺少运行前检查和成本预估

启动前应提示：

- 哪些专家会使用已有实例，哪些会临时派生；
- 哪些软件、MCP 或数据缺失；
- 预计并发数、模型调用、耗时和计算资源；
- 是否包含人工审批；
- 是否存在未替换的任务参数；
- 是否允许以降级模式运行。

### P2-09：轮询失败后静默停止

状态卡连续三次请求失败后停止轮询，但没有明确告诉用户已经停止自动刷新。
建议显示连接状态，使用带上限的指数退避，并提供恢复入口；长期应改用 SSE
或 WebSocket 推送节点事件。

### P2-10：现有专家团文档已经过期

`expert-teams.md` 仍描述三种模式、`chat_with_agent` 和旧启动流程，与当前
OMP 六类编排和状态机实现不一致。

**方向**

- 本评审通过后重写功能文档；
- 从代码或工作流 schema 生成模式、字段和 API 参考，减少再次漂移。

## 7. 建议的后端边界

```text
Expert Registry
  管理专家模板、版本、实例绑定和健康状态

  管理专家团定义、成员绑定策略、版本和历史

  执行开放式多专家讨论、临时派生、分歧与共识形成

  管理工作流定义、版本、发布、复制和权限

Workflow Planner
  将模板和输入实例化为本次运行计划

OMP Scheduler
  在协作工作流调度器约束内执行专家节点和专家团讨论节点

Workflow Scheduler
  确定性执行节点、依赖、并行、条件、循环、审批和汇聚

  强制权限、数据质量、验收规则、预算和人工审批

Artifact & Evidence Store
  保存数据引用、脚本、模拟输入输出、报告和证据链
```

## 8. 建议的前端信息架构

### 8.1 侧边栏入口

侧边栏现有“专家”入口统一改名为：

> **专家·协作**

不再为专家团或协作工作流增加新的侧边栏项，避免领域能力被拆成多个松散页面，
同时保持主导航简洁。

### 8.2 模块内一级入口

“专家·协作”模块顶部设置三个并列一级入口：

```text
专家 | 专家团 | 协作工作流
```

这三个入口应当使用路由或可恢复的页面状态，而不只是临时组件状态。刷新、分享
链接和浏览器前进后退后，应能回到同一个入口和 Tab。

建议路由形态：

```text
/ugsci-experts/experts
/ugsci-experts/teams
/ugsci-experts/workflows
```

如需保持现有 `/ugsci-experts` 兼容，可将其重定向到专家默认 Tab。

### 8.3 “专家”入口及 Tabs

建议包含：

1. **专家实例**：当前已经创建并可直接运行的 Agent；
2. **专家模板**：油气与储气库专业能力模板；
3. **健康与评测**：模型、技能、MCP、软件、权限和质量验证；
4. **最近任务**：单专家任务历史及质量反馈。

第一阶段可以先落地“专家实例”和“专家模板”，健康状态作为卡片和详情的一部分；
待评测体系成熟后再拆出独立 Tab。

专家详情内部再分为：

```text
概览 | 角色与提示词 | 技能 | 工具/MCP | 知识 | 软件 | 权限 | 评测 | 运行历史
```

### 8.4 “专家团”入口及 Tabs

专家团聚焦开放式多专家协同和 OMP 工作流，建议包含：

1. **预设专家团**：平台提供并经过验证的领域团队；
2. **自定义专家团**：用户创建的角色组合和讨论策略；
3. **进行中的讨论**：当前 OMP 阶段、参与角色、事件和中间结论；
4. **讨论历史**：已完成讨论、共识、分歧和证据摘要。

专家团详情建议包含：

```text
概览 | 成员与绑定 | 协作策略 | 任务模板 | 讨论记录 | 运行历史 | 版本
```

进行中的讨论界面应突出：

- 讨论目标和当前议题；
- 固定实例、临时派生角色及其状态；
- 每位专家的核心观点和证据；
- 当前分歧、共识程度和待补充信息；
- OMP 当前阶段、重试和派生记录；
- 最终联合结论、少数意见和不确定性。

### 8.5 “协作工作流”入口及 Tabs

协作工作流聚焦流程化、可版本化、可观测和可治理的任务，建议包含：

1. **工作流模板**：经过验证的生产和科研流程；
2. **我的工作流**：个人或项目的草稿、已发布和已停用定义；
3. **运行中心**：运行中、等待审批、失败、已完成的工作流实例；
4. **组件库**：专家节点、专家团节点、工具节点、质量门和子工作流。

第一版可先提供“工作流模板 / 我的工作流 / 运行中心”，组件库先内置在编辑器，
等节点资产达到一定规模后再拆成独立 Tab。

工作流详情/编辑器建议包含：

```text
基本信息 | 输入输出 | 流程编排 | 角色绑定 | 工具与数据 | 质量与审批 | 版本 | 运行历史
```

运行中心需要支持：

- 按项目、区块、井、储气库和任务类型筛选；
- 节点级状态、输入输出、工具调用和日志；
- 暂停、取消、恢复、重试和人工审批；
- 实际执行路径与定义拓扑对比；
- 结果、证据、风险和质量结论；
- 与聊天会话互相跳转，但不依赖聊天页面才能查看状态。

### 8.6 三个入口之间的组合关系

```text
专家模板/专家实例
    ├── 组成专家团
    └── 绑定到协作工作流节点

专家团
    ├── 独立发起开放式讨论
    └── 作为“专家团讨论节点”嵌入协作工作流

协作工作流
    ├── 固定绑定专家实例
    ├── 按模板临时派生专家
    ├── 动态路由专家
    └── 调用专家团完成开放研判
```

工作流负责规定必须经过的控制点；OMP 负责在允许范围内完成专业任务、动态协作
和开放研判。

### 8.7 领域任务入口

用户不一定先选择“哪个 Agent”。可以从业务任务开始：

- 我要评价一个储层；
- 我要复核开发方案；
- 我要分析某储气库本周期运行；
- 我要诊断注采异常；
- 我要对模拟模型做历史拟合；
- 我要调研某个科研问题并验证一种方法。

平台根据任务模板推荐工作流、输入数据和专家角色。

## 9. 分阶段改造建议

### 阶段 A：在现有架构下完善专家与专家团

建议优先解决：

1. `P0-01` 启动按钮逻辑冲突；
2. `P0-02` 稳定 ID；
3. `P0-03` 明确 `role_key`；
4. `P0-04`、`P0-05` 专家团后端单一真源和稳定团队 ID；
5. `P0-06` 专家创建事务化；
6. 固定绑定、优先绑定、临时派生三类专家团成员策略；
7. 专家健康摘要、专家团可执行性检查和完整 CRUD；
8. 开放讨论的观点、证据、分歧、共识和历史展示；
9. 侧边栏改为“专家·协作”，先落地“专家”和“专家团”两个入口；
10. `P2-10` 文档同步。

阶段验收：团队不会因名称相似误绑定；自定义专家团在刷新、换设备和多次运行后
仍保持一致；创建失败不会留下可见的半成品专家；用户可以明确看到已有实例、
临时派生角色、讨论过程和联合结论。

### 阶段 B：建设独立的“协作工作流”模块

建议解决：

1. 在“专家·协作”中启用第三个一级入口“协作工作流”；
2. `P0-07` 定义正式 `WorkflowDefinition v1` 和 DAG/schema；
3. 建立专家节点的固定实例、模板派生和动态路由绑定；
4. 建立“专家团讨论节点”，复用阶段 A 的 OMP 开放协作能力；
5. `P0-08` Gate/调度器强制执行运行参数；
6. `P1-01` 正式运行 API；
7. `P1-02` 工作流 CRUD、版本和发布管理；
8. `P1-03` 运行中心、运行索引和控制接口。

阶段验收：同一版本工作流的执行拓扑可预测、实际路径可查看、失败后可从节点恢复，
前端展示与后端真实状态一致。

### 阶段 C：建立油气与储气库领域流程闭环

建议解决：

1. `P1-04` 领域数据契约；
2. `P1-05` 证据与结果契约；
3. `P1-06` 人工审批；
4. `P1-10` 生产/科研工作流模板；
5. 计算软件、数据平台和标准规范适配。

阶段验收：至少选取一个生产场景和一个科研场景完成端到端验证，例如：

- 生产：储气库周期运行分析与注采建议；
- 科研：多模型历史拟合方法对比与可重复性验证。

### 阶段 D：优化使用效率和平台运营

建议解决：

- `P2-01` 专家聚合接口；
- `P2-02`～`P2-09` 页面、向导、推送和运行前检查；
- 专家与工作流评测、质量指标、成本和资源指标；
- 模板发布、共享、权限和审计。


对于生产类能力，还应回答：

- 错误结果可能造成什么后果？
- 哪些步骤必须确定性执行？
- 哪些工具调用需要人工审批？
- 数据、模型、软件和结论如何追溯？
- 失败后是终止、降级还是回滚？

对于科研类能力，还应回答：

- 是否保留原始数据和代码环境？
- 能否独立复算？
- 是否记录负结果、替代假设和不确定性？
- 文献和外部事实是否有来源？
- 图表和报告能否从产物重新生成？

## 11. 暂不建议立即做的事情

- 不继续通过增加更多模式枚举来代替工作流 schema；
- 不先做复杂拖拽画布，而后端仍只接受自然语言提示；
- 不把所有专业软件都接入后再处理数据契约和权限；
- 不用更多技能标签代替专家质量评测；
- 不让 LLM 自己决定生产系统的最终外部写入；
- 不一次性推翻现有 OMP Gate，应先建立兼容层和迁移测试。

## 12. 2026-08-02 首轮改造落地状态

本轮已在现有架构上完成阶段 A 的主要基础项，并启用阶段 B 的首个可运行版本：

1. 侧边栏统一为“专家·协作”，内部设置“专家 / 专家团 / 协作工作流”；专家入口
   的既有卡片、详情和配置能力暂不重构；
2. 专家团采用后端单一真源和稳定 ID，补齐查询、详情、保存、更新、删除及旧浏览器
   缓存迁移；
3. 专家团支持顺序交接、并行汇聚、主管协作、智能路由、评审迭代和多方论证六类
   OMP 策略；
4. 成员保存稳定 `agent_id`、显式 `role_key` 和 `fixed / preferred / temporary`
   绑定策略；固定实例直接调用指定 Agent，优先实例允许不可用时降级派生，临时成员
   由 OMP 派生；未知角色失败关闭到受限分析角色，不再静默扩大为全工具执行者；
5. 增加“进行中的讨论 / 讨论历史”和后端运行索引，修复控制器稳定绑定、运行启动
   重复注册、评审轮数未强制、状态读取竞态等问题；
6. “协作工作流”复用 FlowForge 的 DAG、CRUD、校验、运行、持久记录、事件流、取消
   与恢复能力，并提供工作流模板、我的工作流和运行中心；
7. 支持从自由自然语言 SOP 或领域模板生成可编辑工作流草稿；生成的顺序节点会传递
   上一步产物，领域模板按可用专家实例生成节点级固定绑定和角色元数据；
8. FlowForge 不再注册独立顶级侧边栏菜单，只由“专家·协作”进入，但保留可分享的
   工作流和运行详情 URL。

下一步优先补齐开放讨论产物模型和“专家团讨论节点”，再建设正式工作流发布版本、
人工审批、领域输入输出契约，以及生产与科研场景的端到端验收。
