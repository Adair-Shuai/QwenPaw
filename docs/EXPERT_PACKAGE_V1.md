# 专家包首版实现与接入

状态：开发实现，已补充发布加固与 Awsome-tools 接入代码；尚未发布桌面安装包、部署新发布服务或上传正式 UGSci 渠道。完整方向见 `docs/EXPERT_PACKAGE_DESIGN.md`；本文件描述当前实现边界。

## 已实现

- 市场条目提供 `package_manifest` 时进入专家包安装流程；没有该字段的旧模板保留原有创建行为。
- 后端下载渠道清单及 `.sig`，使用受信 Ed25519 公钥验签，检查核心最低版本、系统/架构、Python 主次版本。
- 签名清单包含完整文件摘要、归档摘要/大小、技能路径、精确 wheel 文件集合、MCP 入口、工具契约摘要及真实方法自检。
- 依赖仅从包内 wheel 安装到独立 venv；校验活动传递依赖与 extras，拒绝缺失依赖、不兼容版本、直接 URL 和不匹配平台 wheel。安装阶段不访问 PyPI，不编译源码，不修改宿主依赖。
- 桌面使用现有 `QWENPAW_DESKTOP_PY_RUNTIME` 选择独立 CPython；冻结主程序不会被误当成 Python 解释器。开发环境使用当前解释器。
- 任务有持久状态、进程间锁、重复提交保护、失败重试、下载复用、中断恢复与取消。正常关闭宿主时等待正在进行的步骤安全收尾。
- 技能使用现有安装服务与扫描机制；MCP 通过真实 stdio 握手、工具契约检查和结构化结果断言后，才保存 DriverCard 并登记专家。
- 验证使用临时工作区。专家实例采用现有配置事务登记；在登记后、任务完成前发生中断，重试保留用户改过的说明文件。
- 前端显示下载、准备、自检、登记和就绪状态；离开再回到市场可恢复查看任务，并显示可选能力仍需配置的说明。
- 登记后等待宿主启动，并从实际 DriverManager 核对方法工具；默认对话模型未选择、必需技能未启用或工具不可用时显示启动检查失败，可只重试启动。新宿主进程不沿用旧的运行就绪标记。模型检查仅核对选择配置，不证明凭证有效、服务在线或模型回答质量。
- 新建专家工作区使用随包身份说明，不生成普通智能体的首次身份问答模板；已有用户工作区不批量重写。

## 油藏专家试点

`scripts/prepare_reservoir_expert.py` 从已有的 `packages/ugsci-reservoir-expert` 和 `packages/ugsci-reservoir-io` 生成独立 payload 与本机平台 wheelhouse。包含六个技能、基础读写库和方法 MCP；不包含私有手册、用户模型或商业模拟器。

`package_server.py` 在基础版中不暴露尚未配置的私有知识检索工具。自检实际计算已知现金流 NPV，并通过读写库写出、重新读取带压力单位的表格，核对数值、单位及校验状态。

构建机操作：

```powershell
.venv/Scripts/python.exe scripts/prepare_reservoir_expert.py --output <全新的暂存目录>
.venv/Scripts/python.exe scripts/build_expert_release.py --source <暂存目录>/payload --spec <暂存目录>/recipe.json --output <发行目录>
```

第二步从发布环境的 `UGSCI_EXPERT_SIGNING_KEY` 读取 Base64 Ed25519 私钥。构建器在目标平台安装离线依赖并执行真实 MCP 自检，通过后才签名输出。私钥不会写入发行目录；不得使用测试公钥替换正式信任根。

产物结构：

```text
expert-packages/
  artifacts/<归档 SHA-256>.zip
  manifests/<清单 SHA-256>.json
  manifests/<清单 SHA-256>.json.sig
```

正式发布需要在现有渠道审核流程中上传这三项不可变产物，最后更新 `agents/manifest.json` 的相应条目：

```json
{
  "id": "ugsci.reservoir-simulation-expert",
  "name": "油藏数值模拟专家",
  "description": "基础读写、评分、实验设计和方案评价",
  "tags": ["油藏工程"],
  "package_manifest": "expert-packages/manifests/<清单 SHA-256>.json"
}
```

示例中的摘要必须替换为构建器返回的真实 `manifest_path`。直接引用单平台清单仍兼容；新发布流程把此字段指向 `expert-packages/indexes/<摘要>.json`，客户端先验签索引，再按系统、架构和 Python 选择已签名的平台清单，并核对内容摘要、专家身份和版本。没有匹配平台时明确拒绝。

生产默认渠道为现有 UGSci 工具 OSS，默认公钥复用发布信任根。测试/受管理部署可以通过 `UGSCI_EXPERT_CHANNEL_URL` 和 `UGSCI_EXPERT_PUBLIC_KEY` 配置独立 HTTPS 渠道与公钥；普通请求只能提供渠道内相对路径，不能指定任意下载域名或自带信任公钥。

## API

| 路由（均位于 `/api` 下） | 用途 |
| --- | --- |
| `POST /expert-packages/plan` | 输入 `manifest_path`，返回已验签的下载量、技能/工具及安装 ID |
| `GET /expert-packages/installations` | 恢复查看本地安装任务 |
| `POST /expert-packages/installations/{id}` | 开始或重试同一任务 |
| `GET /expert-packages/installations/{id}` | 查询阶段与结果 |
| `POST /expert-packages/installations/{id}/cancel` | 在安全阶段边界取消；登记阶段不取消 |

安装计划与任务保存在用户工作目录的 `expert-packages/jobs`。目录使用摘要前缀缩短 Windows 路径，但元数据和身份检查始终使用完整摘要。已下载归档和环境可复用；不能直接删除其中已被专家绑定的工作区或运行环境。

## 首版边界

- 当前支持单个本地 Python MCP 服务、随包技能与完整离线 wheelhouse；使用宿主提供的 Python，不单独下载另一版本 Python。
- 本次实现安装和受信发布闭环，并支持签名多平台索引。跨专家共享依赖仓库、版本内升级/回滚、自动卸载回收、签名吊销/密钥轮换、Node/Java 包、远程 MCP/OAuth 自动装配尚未实现。新版本包会创建独立实例，不覆盖已有实例。
- 可选商业模拟器、知识索引和二进制格式依赖仍使用原有配置入口；此安装器只说明前置条件，不替用户安装许可证或导入私有资料。
- 子进程和 venv 用于依赖隔离，不是 OS 沙箱；只接受受信发布者签名的包。
- 同一签名清单重复安装复用实例，不重置用户配置。本地构建记录与渠道不可变发行记录共同拒绝同版本不同内容；一次渠道发行固定该版本的全部平台，增加平台也需升版本。删除专家后可重新登记，保留已安装工作区的用户修改及工具启用设置。首次下载中断会重新下载该归档；已核验的完整归档与后续阶段可以恢复。当前没有 HTTP 字节断点续传。
- 需要把新后端与 UGSci 插件一起交付。旧宿主缺少 API 时前端提示失败，不回退成只有提示词的专家。
- Windows 开发环境已做真实构建和安装验收；macOS 干净机器及正式桌面包内的安装尚需平台验收，不能由跨平台代码推导为已验证。

## 发布牢固性复核（2026-11-16，修复前记录）

结论：具备受信专家包首装能力，尚不满足正式渠道持续发布的验收条件。本次是检查，没有修复下列问题，也没有访问或修改生产渠道。

在独立临时用户目录中，使用临时签名密钥、真实构建器、离线依赖安装和 MCP 子进程复现了四项缺口（本地证据 `.codex-tmp/expert-package-audit-findings.json`；复现程序 `expert-package-audit-probe.py` 位于同目录）：

1. 同一专家 ID、版本、平台下修改说明文件，两份不同内容均可构建签名。摘要地址保护了单个文件的不可变性，但没有保护发行版本唯一性。发布前需按 ID／版本／平台／Python 记录内容身份，冲突时拒绝，并锁定构建依赖。
2. 在测试 wheel 中加入无真实秘密的 `example_method/.env` 标记，构建、签名和安装全部通过。当前私有文件检查只遍历外层 payload，不检查 wheel 内部；普通文件名中的密钥内容也不受路径规则保护。需要嵌套制品审计、秘密扫描和明确的资源允许清单，且不能粗暴禁止科学库所需的一切 data 目录。
3. 声明一个工具，MCP 返回两个工具，构建及安装仍通过。`runtime.verify` 只检查声明工具是否为返回集合的子集，绑定 DriverCard 时未设置工具范围。需要准确匹配声明工具并在实际运行绑定中限制暴露范围；现有 DriverPolicy 的默认询问仍在，这不是任意工具绕过用户批准的证明。
4. 成功安装后按现有删除接口的方式移除专家配置，再次安装返回 `ready`，但专家没有恢复。`start` 在状态为 `ready` 时直接返回，未核对当前专家、环境和运行状态。需要删除联动、重新安装及保留用户定制的修复流程；宿主 Python 升级后也需专门验收环境有效性。

发布运维尚缺：专家包专用上传器及 CI（上传前再验签／校验实际内容、远端同版本冲突预检、不可覆盖上传、下载回读、最后并发安全更新目录、失败时保留旧目录）；签名的多平台目录与宿主能力选择；发行撤回／吊销和密钥轮换；真实桌面包及 macOS 原生验收。现有插件 ZIP 上传器仅消费插件 `index.json` 和 `files/plugins/` 路径，不能视为已覆盖专家包。构建器当前也允许任意传入私钥自验通过，正式发布入口需要核对预期渠道公钥。

复核时重新执行现有专家包专项：14 项通过。上述新增复现说明原专项尚未覆盖这些场景，不能将通过结果当作正式发布已牢固的证据。

## 复核问题修复与 Awsome-tools 接入

本节是上述复核之后的实现状态。四个复现已有行为回归：本地和线上版本冲突拒绝、嵌套 wheel 私有文件拦截、MCP 工具集合准确匹配并写入运行时工具允许清单、删除后重装保留用户说明/技能/工具停用选择。运行环境缺失或宿主 Python 身份变化会显示修复提示，要求先删除专家配置再重新安装，不在线改写正在运行的环境；保留工作区，重新安装时重建依赖。

嵌套包检查有展开字节数、文件数、深度和路径/链接限制。科学库的 data 资源及公开证书允许存在；发现已知私有文件或高置信度凭证格式时拒绝，日志不回显秘密。此检查不能证明任意代码无恶意，也不能识别所有隐写或自定义凭证格式。

新增三个管理员接口，复用现有发布服务的身份验证、专家 OSS 桶、跨进程写入锁、不可覆盖写入和回读校验：

| 接口 | 用途 |
| --- | --- |
| `POST /v1/expert-packages/releases/inspect` | 验签、核对全部平台产物及远端版本冲突，不上传发行对象 |
| `POST /v1/expert-packages/releases` | 再次校验，上传并回读全部不可变对象，最后更新目录 |
| `POST /v1/expert-catalog/import` | 合并 Awsome-tools 旧模板元数据，保留已发布专家包及他人投稿条目 |

单次发行的全部 ZIP 总计最多 256 MiB，复用现有 360 MiB JSON 请求上限。预检会短暂获取并释放目录写入锁。发布服务不执行包内代码；真实自检在无发布凭证的原生构建任务中完成。上传制品失败不推进目录；目录写入后网络/回读异常属于未确认提交，需回读核对后重试，不能把它自动解释为未生效。

`scripts/expert_channel/Awsome-tools/` 提供另一仓库的配套修改：

- `expert-release.yml`：手动选择配方，默认仅构建；按配方的平台矩阵运行真实自检。单独的新任务再检查、签名并发布，签名私钥不进入执行专家代码的构建任务。
- `sync-to-oss.yml`：取消 agents 区域的删除同步并排除 `manifest.json`，目录统一经服务合并。没有服务配置时明确失败，不回退成直接覆盖目录。
- `experts/version-demo/`：可执行的 Python 3.11 演示配方，依赖精确版本与 SHA-256 固定。现有 PVT/油藏等模板不自动转换为已验证包。

正式启用顺序：交付包含本实现的宿主与发布服务 → 将 QwenPaw 工具链固定到已交付的 40 位提交 SHA → 配置 Awsome-tools 的只读跨仓库凭证、发布 Environment 和服务地址 → 合并渠道工作流 → 先运行不发布的三平台构建及桌面验收 → 再显式发布。配置名称和 RAM 路径见配套 `experts/README.md`。本次不自动修改生产秘密、OSS 权限或市场目录。

原生构建使用 `prepare_expert_recipe.py` 消费完整哈希锁，再执行 `build_expert_release.py --unsigned`；签名任务使用 `seal_expert_release.py`，核对预期渠道公钥并生成签名多平台索引；上传使用 `publish_expert_release.py`，先预检再提交。服务会拒绝旧模板发布入口覆盖已转换为签名包的专家。

## 开箱即用系统复核（2026-11-16，发布加固之后）

结论：当前支持“受信 Python 专家包的可验证安装”，尚不能将所有市场专家承诺为开箱即用。用户应能在已配置平台对话模型的前提下，选择专家、安装、直接完成该专家声明的基础任务，而不必寻找作者电脑路径、手工配置 Python/MCP 或重新定义专家身份。商业许可证、外部账号和用户私有数据需要用户提供，但必须在使用前说明，不能在执行中才暴露隐含依赖。

本次沿市场、安装、配置登记、首轮提示、宿主工具调用、重启和发布边界检查，修复以下问题：

1. **登记即误报就绪**：此前未等待 `schedule_agent_startup` 返回的 Task，异步失败也可能显示绿色。现在等待启动并检查真实工具目录，增加 `starting`／`startup_failed`，失败后重试不重装依赖、不覆盖用户说明。旧进程的成功记录不当作新进程已加载的证据。
2. **首次身份问答冲突**：普通初始化模板生成 `BOOTSTRAP.md`，会在首轮用户消息前加入身份设置指令。新专家工作区不再生成这套模板。
3. **进度查询读到缓存**：1.5 秒轮询曾经过 15 秒通用 GET 缓存，状态变化延迟。进度查询现在绕过缓存，实际打包页面覆盖启动失败及重试，不靠延长测试等待时间掩盖问题。

## 渐进完善第二步：保留实例的运行环境修复

市场的失效环境、方法服务不可用和修复失败状态提供“修复运行环境”。接口为 `POST /expert-packages/installations/{job_id}/repair`，复用安装任务身份和跨进程安装锁。重复请求合并为同一个任务；修复前重新验证原签名清单、平台/Python 兼容性与本地方法包完整文件摘要。此版修复同版本 Python 依赖环境，要求原签名方法包缓存完整；不下载替换损坏的方法包，不升级专家版本。

新依赖在独立的最终目录中安装，使用离线 wheel，在临时工作区执行真实 MCP 工具契约和方法自检。通过后只原子替换现有方法配置中的 Python 启动路径，不搬迁虚拟环境。专家 ID、工作区、业务文件、自定义说明和技能、工具范围、审批策略、凭证引用、用户环境变量及启用/停用状态保留。配置按读入版本比较后写入，修复期间用户改过配置则拒绝覆盖；自定义启动命令或参数也不自动改写。

运行中、启动中或尚未完成清理的专家拒绝修复，提示先在专家中心停用。提交前再次检查状态并取得维护锁，阻止新启动；即使宿主在原子写入期间取消任务，也必须等文件写入完成才释放锁。此版不自动停止用户任务、不自动启用专家。修复成功显示“运行环境已修复，可检查启动”，随后仍需通过模型、技能和实际方法服务的启动检查才能显示就绪。

实际方法配置是当前环境的唯一选择依据；每个新环境先落盘保存宿主身份和验证结果，再切换配置。若提交完成后宿主中断，重新修复会识别已切换环境并恢复任务状态，不重复创建专家或依赖环境。提交前取消或验证失败保留原启动路径。旧环境与未采用的候选目录暂时保留，自动回收和版本回滚留待后续实现；修复自检的临时工作区会清理。
