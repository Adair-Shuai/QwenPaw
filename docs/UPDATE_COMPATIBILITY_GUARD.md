# 后续发布的更新兼容保护

目标是让当前软件持续具备跨版本升级、差量失败后的全量恢复、用户数据保留及兼容检查能力；不以追溯安装过去十个桌面版本作为本次验收条件。

## 固定检查入口

```text
python scripts/verify_update_regressions.py
```

使用项目虚拟环境运行。该命令先确认必需测试文件与关键用例仍在，再执行更新器、客户端、发布产物、安装器交接、恢复和工作流回归。普通后端 CI 与发布的完整测试门禁先运行 `--check`，再由已有的跨平台完整单元测试执行这些用例，避免重复跑同一套测试。

新增的升级契约测试使用真实发布器生成临时签名更新包，经当前客户端的签名指针、清单、下载缓存、校验和原子安装流程消费。仅网络传输使用隔离测试响应，不连接线上、不改用户安装目录。覆盖：

- 匹配历史基线时应用差量；基线缺失、被修改或差量下载失败时使用签名全量包。
- 全量恢复仍然保留用户模型配置和工作区记录；全量包损坏时旧代码和用户数据保持可用。
- 升级成功后再次检查不会重复安装。
- 宿主协议、宿主指纹或最低版本不兼容时，阻止组件下载和激活，保留完整桌面更新路径。
- 现有回归继续验证备份失败阻止安装、中断恢复、健康确认前保留上一版本以及 Windows 安装交接约束。

## 实际发布产物门禁

`scripts/pack-tauri/verify_component_release.py` 由组件构建流程以及上传／提升流程分别执行，任何错误都会阻止后续步骤。检查：

1. 清单与所有实际 ZIP 的签名、SHA-256、长度、目标平台和兼容策略。
2. 每个组件必须提供全量恢复包，包内受管文件的完整清单与内容摘要必须吻合。
3. 差量包的来源／目标版本、基础／目标文件清单、增删改操作与实际文件内容必须一致；不得修改受保护数据。
4. 不安全路径、链接、重复文件、损坏 ZIP、缺失文件及指向发布目录以外的地址均拒绝发布。

构建器原有的逐个历史基线真实应用差量检查继续保留。历史不足或没有合适差量时允许全量更新，不将“必须存在十个旧版本”作为发布前提。

## 维护约束与边界

- 仓库自有应用和插件的宿主兼容上限统一为 `<3.0.0`，保留各自最低版本及 SDK／组件协议约束；源码与内置打包副本保持一致。`test_shipped_plugins_keep_major_version_compatibility_boundary` 验证后续 2.x 不因过窄上限被禁用，同时拒绝 3.0 正式版与预发行版。这是发布兼容声明，不替代对实际宿主接口的行为回归。

- UGSci 的 `visualization/data` 仅是本地可视化测试数据。插件清单、桌面／组件暂存、Python 包、源码包和 Docker 上下文均排除它；打包镜像同步也不得复制该目录。组件签名发布检查、桌面产物检查和插件市场打包检查遇到这类数据必须失败。`test_ugsci_release_data.py` 验证实际产物，以及无预置数据时的可视化导入能力。

- 最低兼容版本和组件协议维护在 `scripts/pack-tauri/component_compatibility.json`，不要跟随每次发布版本机械递增，也不能为了通过检查而降低协议门槛。
- Beta 9 的最低核心版本为 `2.2.2b9`：这次新增了对 UGSci 历史 `visualization/data` 用户导入目录的保留能力。旧核心不理解该受保护子目录，必须先完成桌面更新再激活插件，避免旧版全量替换丢失导入数据。该目录仍严格禁止进入任何发布包。
- 原生宿主、安装器、权限或签名策略改变时，保持主程序指纹与桌面完整更新路径。不得绕过签名或错误降级到不兼容组件。
- 前端的最新状态、版本说明、组件状态检查由 `console` 中的 `npm run test:fork-features` 保留。
- 校验失败必须修复包或代码；不得删除／跳过关键测试或在工作流添加容错放行。
- 宿主管理的 OfficeCLI 调用和构建期版本探测必须传入 `OFFICECLI_SKIP_UPDATE=1`，防止引擎后台自更新替换已审定的二进制。构建验证在执行版本探测后再次核对锁定 SHA-256；不能只相信版本标记文件。真实引擎测试同时核对执行前后的摘要，并保留 Word、Excel、PowerPoint、预览与宏内容保留回归。
- 当前改动增加自动防错措施，不代表任何系统都能承诺永远没有故障。完整桌面安装包仍由现有 Windows／macOS 构建和安装启动检查验收；本次本地验证不等于执行线上发布。

## 兼容声明与运行时升级回归

- 安装包内置目录作为插件更新源时，必须与本机官方目录中的精确路径、插件 ID、版本及宿主兼容性匹配；不能把任意本地目录加入外部下载白名单。更新沿用原生生命周期、活动任务确认、备份与失败回滚。插件启动失败只改变实际运行状态，必须保留用户的启用意图，允许兼容的新版本恢复运行；显式禁用不能被失败恢复改写。`test_plugins_router.py` 验证真实目录替换、失败插件恢复、忙碌确认和损坏候选回滚，`test_plugin_config_update.py` 验证启用与禁用意图，均纳入固定更新回归。

- 兼容范围、依赖或包内容改变时，必须发布高于原版本的新插件版本；不能在旧版本 URL 上覆盖 ZIP 或修改旧版目录元数据。当前修复将储量应用推进到 0.3.2，并同步其余兼容声明改变的插件版本与内置副本。真实 ZIP 回归核对版本递增及清单／元数据一致，Data 应用先由专用发布任务构建前端，再验证发布包。
- 预发行宿主遇到显式 Beta／RC 最低版本时，前后端均按实际预发行版本比较最低界限；稳定最低版本与独占上界继续按即将发布的稳定版本判断。
- 外部插件替换遇到 plugin_busy 必须返回 409 及原有结构化原因。仅用户确认后传 interrupt_tasks；忙碌拒绝发生在生命周期变更之前，不触发回滚重装。真实加载器回归保护取消前的旧版本和确认后的资源释放。
- 全仓库验收使用 pre-commit run --all-files、控制台 format:check 和固定前后端／更新器回归，不能仅以合并冲突文件的提交钩子结果代替。历史事务及数值算法保留局部复杂度例外，公共回调保留参数名；不修改全局检查门槛或删减测试。

## 插件、应用与组件更新的生命周期约束

- 手动替换的备份、当前版本复读与安装必须处于同一插件生命周期锁内。加载器负责回滚，路由不得再次强制安装旧备份；过期请求不得把已提交的新版本降级。同版本修复仍允许。
- 更新前必须检查宿主兼容性，包括启动时因禁用而没有加载记录的插件。显式禁用允许提交合法候选，但不得执行候选代码或改写用户启用意图。
- 持久提交之后的备份、标记及墓碑清理失败，返回已生效的新版本和明确的待清理诊断；提交之前失败继续走恢复流程。依赖升级确认必须保留结构化操作身份，由用户决定继续或取消。
- 启动恢复必须停止旧实例、孤立运行资源和后台准备任务。只有完整清理且已静止时才允许回滚目录；未停净或健康候选清理失败时保留恢复凭据，不强制移除运行记录。
- 待更新队列使用跨进程短锁和每次请求的独立身份。安装期间允许新请求入队，完成时只确认当前处理的那一代请求，不覆盖同组件的新请求。
- 原生宿主按每次启动的独立回执区分准备中、核心就绪、核心失败及主动更新重启。运行时上一版本的清理只能发生在核心就绪后；可选插件失败不等同核心启动失败。
- 应用列表合并安装文件与运行状态，保留失败、禁用、待启动应用及诊断。前端更新必须按应用身份撤销旧注册并加载新版，加载失败清理部分注册；加载、更新与卸载共用顺序控制，旧清单不得覆盖较新的用户操作。
- 受管应用服务只有通过健康检查且子进程存活才算就绪；进程退出后不得继续提供旧地址，再次启动必须回收旧进程资源。

行为回归由 `test_plugin_update_transactions.py`、`test_bundled_startup_safety.py`、`test_component_service.py`、`test_healthz.py`、`test_pawapp_listing.py`、`test_app_contract.py` 以及控制台的 `usePluginLoader.test.ts`、`AppCenter.updates.test.tsx`、`AppCard.test.tsx` 保护，并纳入固定检查清单。原生回执和旧健康接口兼容性同时由 Rust daemon 测试保护。
